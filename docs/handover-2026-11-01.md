## The split, and why

Rahman's decision on 2026-11-01: **do not make them alike.** Two repositories, same scope,
different techstack.

- **codex-desktop** — configuration and tooling for OpenAI's Codex Desktop (Rust + Electron).
  Is not, and will not become, a clone of that binary; it drives the real one.
- **codex-web** — SvelteKit console. Not an agent. Execution reaches the user's machine only
  through the bridge in `docs/terminal.md` / `bridge/terminal-bridge.mjs`.

The origin of the confusion: the web UI was reconstructed from **screenshots** of the desktop
app, and much of it was reconstructed wrongly. Do not treat the existing views as a spec.

Root causes worth not rediscovering:

- `collaboration` namespace is flattened by the gateway's Responses→Chat translator for
  non-OpenAI upstreams → sub-agents die with `unsupported call: collaboration`. **Scope was
  understated:** the shipped `codex.exe` declares two member lists totalling ten members plus a
  message board, not the six one capture showed. A gateway fix built on the six observed names is
  incomplete. See `docs/rea-rust-binaries.md` §1.
- Images through a non-OpenAI upstream are **unstable, and the earlier mechanism was wrong.**
  This document used to say the model swaps to `kimi-k2.7-code` and the base64 is tokenised as
  text. Neither reproduced on 2026-11-01: `kimi` appeared 0 times, there was no prompt-too-long
  error, and `input_image` was present in the rollout. What actually happens is that `ctx/*`
  receives the image, can even name a marker drawn on it, then degenerates — 2 of 3 runs ended
  with **no answer at all** (one at 10.9k tokens after calling `view_image`, one at 256k in a
  loop). `cx/*` answered 3 of 3 at ~17.3k tokens. Advice is unchanged: **use `cx/*` for anything
  with an image.** The reason is instability, not a model swap. Full evidence:
  codex-desktop `docs/PROGRESS.md` §5i.
- Windows sandbox banner ("Couldn't check Windows setup") is cosmetic.
  `HKLM\SOFTWARE\OpenAI\Codex\WindowsSandboxService` binds provisioning to one `CODEX_HOME`.
  Do not edit that registry key; it strips the sandbox from the real account.
- `Access is denied (os error 5)` on plugin cache = `chrome@openai-bundled` enabled in the clone.
  Chrome launches `extension-host.exe` from inside the cache directory and Windows locks it.

Two traps found the hard way:

- Setting the only stub backend's `ready` to `false` to stop the console claiming a device also
  makes `initialBackend()` return `""`, so no backend is selected and the composer can never send.
  Honesty belongs in `stub: true` + `reason`, not in `ready`. Caught by `dev-smoke`, not by unit
  tests — nothing unit-tests the shell→composer path.
- `Chat.svelte` read a provider key from `localStorage.getItem("byok-key")`, which contradicts
  `docs/byok.md` §1 and which nothing wrote, so the SvelteKit BYOK path always failed its
  `parseChat` validation. **Fixed 2026-11-02** — see below.

| Registry                    | `memories`, `git` registered; access rules in `feature_access.ts`            |

`src/lib/byok_key.ts` is the only place a SvelteKit-path key lives. The alphabet it accepts is
the `keySchema` alphabet, so the route is never handed a body it must reject. It is not
`localStorage`, not `sessionStorage`, and it dies with the tab; the Convex path is still the one
to use when the key must survive a reload.

The git surface is deliberately partial: `GIT_SURFACE_ENABLED=true` plus a `GIT_SURFACE_ROOTS`
allowlist buys status and `log -n 20` through `execFile` with a fixed argument array. Stage,
diff, commit and push need a process boundary and an approval model that this build does not
have. Do not describe it as a git client.

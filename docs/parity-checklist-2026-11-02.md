# Parity checklist and techstack migration plan — 2026-11-02

Two repositories, one scope, deliberately different techstack
(`codex-desktop/README.md`). This document compares what each one actually has, then plans how
feature gaps get closed **in codex-web's stack** — not by porting Electron code.

Baselines read for this document:

| Side          | Tree                                               | Evidence                                                                           |
| ------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| codex-desktop | `c3cd3c0`                                          | `parity-evidence/capability-matrix.txt` (241 lines), `docs/PROGRESS.md` §3, §5h–5i |
| codex-web     | this tree, `1ab435b` + uncommitted 2026-11-02 work | `docs/view-audit-2026-11-01.md`, route/module census                               |

Three labels are used throughout, and they are not interchangeable:

- **PASS / BLOCKED** — measured at runtime on the desktop side.
- **compiled-in** — the Rust binary declares the capability and its config surface; the UI may
  still not expose it (`docs/rea-rust-binaries.md` §4).
- **real / partial / stub / guess** — codex-web's own audit scale
  (`docs/view-audit-2026-11-01.md`).

A compiled-in desktop capability is **not** a passing feature, and a codex-web `real` view is not
a parity feature either. Both columns say what they measured.

## 1. Checklist

Verdict column: `parity` = both sides have it working; `partial` = one side is weaker or a piece is
missing; `gap` = codex-web does not have it; `n/a` = the capability has no meaning without a native
process; `blocked` = measured as refused on the desktop side too.

## 2. What actually migrates, and what does not

"Migrate the techstack" here cannot mean porting Electron to SvelteKit. The desktop app's
advantages come from being a native process, not from its UI framework. Only the **contracts**
migrate.

| Desktop asset                                                 | Portable to codex-web? | Why                                                            |
| ------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------- |
| Approval-policy model (`Never/OnRequest/Granular/AutoReview`) | yes, as policy data    | Already exists as UI; needs server enforcement                 |
| Sandbox modes (`ReadOnly/WorkspaceWrite/DangerFullAccess`)    | partly — names only    | Web has no OS sandbox; the bridge process does                 |
| `apply_patch` semantic (unified diff, verified on disk)       | yes                    | Pure text-in / filesystem-out, needs the bridge                |
| MCP App host host↔guest message protocol                      | yes, as a design       | Implement as sandboxed `<iframe>` + `postMessage`              |
| Memories config surface (`dual_write`, `max_unused_days`)     | yes                    | Becomes Convex columns + a cleanup job                         |
| `project_roots` as a `FileSystemSpecialPath` variant          | no                     | Rust enum; web needs an allowlist string list instead          |
| asar bundles, IPC channel names, MSIX identity                | no                     | Desktop packaging; nothing in a browser consumes them          |
| `CODEX_HOME` / `--user-data-dir` isolation                    | no                     | Process-level; the web equivalent is surface detection only    |
| `cx/*` vs `ctx/*` upstream choice                             | yes, as guidance       | Image turns must not silently fall back to a vision-less model |

So: **contracts and policies migrate; runtime, sandbox and packaging do not.** Everything below is
implemented with SvelteKit routes, Convex tables and one Node bridge process — no new runtime.

## 3. Migration plan

Ordered by (value closed ÷ cost), with the dependency graph honoured: nothing after Phase 2 is
worth starting before Phase 0 lands, because each one would otherwise invent its own process
boundary.

### Phase 0 — Bridge protocol v2 and a policy store (foundation)

Closes the prerequisite for Phases 1–3. Nothing user-visible.

| Item          | Decision                                                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Wire contract | Extend `bridge/terminal-bridge.mjs` to `/v2/*` with capability negotiation: `health`, `pty`, `exec`, `fs`, `git`                                   |
| Auth          | Same `bearer.<token>` subprotocol for sockets; `Authorization` for HTTP verbs                                                                      |
| Allowlists    | Per-verb allowlists in the bridge env (`BRIDGE_EXEC_ROOTS`, `BRIDGE_FS_ROOTS`, `BRIDGE_GIT_ROOTS`); refuse `..`, resolve symlinks before comparing |
| Policy store  | New Convex table `policies` `{ owner, surface, verb, decision, updatedAt }` — mirrors the desktop `Approval` enum                                  |
| Server guard  | One module `src/lib/server/policy.ts` that every route calls; a verb with no policy row is denied, never defaulted open                            |
| Audit         | Reuse `logEvent`, flat primitives only, no arguments or paths                                                                                      |

Exit gate: `bun run verify` green; a bridge spec proves every verb refuses an unlisted root and
refuses a missing policy; `docs/terminal.md` gains a §"v2 verbs" table.

Cost: **M**. Risk: medium — this is the security boundary, so it lands alone, reviewed.

### Phase 1 — Agent loop with tools (closes 6 rows)

The single highest-value change: it turns the console into an agent.

| Step | Change                                                                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1.1  | `ChatMessage` gains an optional `toolCalls` shape; keep `content` mandatory so existing callers compile                        |
| 1.2  | `src/lib/server/ai/tools.ts` — a registry of 4 verbs: `read_file`, `write_file`, `apply_patch`, `exec`                         |
| 1.3  | `chatResponse` gains a bounded loop: max 8 steps, max 32k output, each tool call gated by `policy.ts`                          |
| 1.4  | Tool results are untrusted text, labelled as such in the next turn (same rule as `decisionNote`)                               |
| 1.5  | Chat shows each step: verb, target, decision (`allowed`/`denied`), and asks for approval inline when the policy is `OnRequest` |
| 1.6  | Parallel tool calls: run at most 2 concurrently, `Promise.allSettled`, same as the desktop clone's route                       |

Explicitly **not** in this phase: sub-agents, worktrees, PR review. Sub-agents need the gateway's
namespace fix (`capability-matrix.txt`) or an OpenAI-native upstream, which is a deployment
decision, not code.

Exit gate: a fixture repo is patched by the model and the file is read back to prove it; a denied
verb produces a refusal the UI shows; `docs/ai-mcp.md` documents the loop and its caps.

Cost: **L**. Risk: high — model-driven writes. Ship behind `AI_TOOLS_ENABLED=false` default.

### Phase 2 — Filesystem and git write path (closes 4 rows)

| Step | Change                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------- |
| 2.1  | `src/lib/server/git.ts` gains `gitDiff` and `gitStage` over the already-allowlisted roots                |
| 2.2  | Commit is a separate verb with a policy gate and a message length cap; refuse `--amend`, `--force`, `-S` |
| 2.3  | Worktrees: `git worktree list/add/remove`, roots still from `GIT_SURFACE_ROOTS`                          |
| 2.4  | `Git.svelte` grows diff and stage affordances, each showing the policy decision first                    |
| 2.5  | PR review stays out: no forge credential in reach. Record it as `gap`, not a TODO                        |

Exit gate: unit specs for diff/stage parsing; one browser test that stages a file in a fixture
repo and reads the index back; refusal test for a root outside the allowlist.

Cost: **M**. Risk: medium — write verbs on the user's repo.

### Phase 3 — Multimodal input (closes 2 rows, prevents a known silent failure)

| Step | Change                                                                                                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 3.1  | `ChatMessage.content` becomes `string \| Array<{ type: 'text' \| 'image'; ... }>` at the route boundary, normalised to text for providers that take text                     |
| 3.2  | `/api/ai/chat` accepts images with a hard cap: 2 images, 4 MB each, `image/png\|jpeg\|webp` only, dimensions read and bounded                                                |
| 3.3  | Never silently downgrade: a provider without image support returns a typed error, matching the desktop lesson that a fallback to a vision-less upstream fails silently       |
| 3.4  | Artifact surface: a sandboxed `<iframe srcdoc>` with no network, capped size, rendered from markdown fences — the desktop equivalent is the `visualize` skill's own rule set |

Exit gate: an image turn reaches a provider and the reply references a detail only visible in the
image (marker-drawn fixture, same technique as `scripts/mk-probe-image.ps1`); an unsupported
provider returns the typed error rather than an empty reply.

Cost: **M**. Risk: medium — cost and latency per turn.

### Phase 4 — Memories and projects to Convex (closes 2 partials)

| Step | Change                                                                                                       |
| ---- | ------------------------------------------------------------------------------------------------------------ |
| 4.1  | Tables `memories { owner, text, createdAt, usedAt }` and `projects { owner, name, instructions, createdAt }` |
| 4.2  | Membership table `projectChats { owner, projectId, sessionId }` — replaces the localStorage map              |
| 4.3  | Keep the local store as an offline cache; `dual_write` becomes a real boolean, default off                   |
| 4.4  | Retention: `maxUnusedDays` on the owner row, cleanup in a Convex scheduled function                          |
| 4.5  | Consolidation stays out. The desktop algorithm is not documented and guessing it is worse than not having it |

Exit gate: migration spec for the localStorage → Convex upgrade path (idempotent, no duplicate
rows); a test proves a stale local note does not resurrect a deleted cloud note.

Cost: **M**. Risk: low — additive tables.

### Phase 5 — Scheduled tasks (closes 1 row)

| Step | Change                                                                                     |
| ---- | ------------------------------------------------------------------------------------------ |
| 5.1  | Table `automations { owner, sessionId, prompt, cron, nextRunAt, enabled }`                 |
| 5.2  | Convex scheduled function drains due rows; each run appends to the **same** session        |
| 5.3  | Hard caps: 20 automations per owner, min interval 15 min, max 3 failed runs before disable |
| 5.4  | UI: reuse the existing `Apps.svelte` surfaces rather than adding a view                    |

Exit gate: a one-minute-interval automation in a test deployment appends two turns and stops after
the failure cap. Do not ship a cron editor before the failure path is proven.

Cost: **M**. Risk: medium — background cost with no user watching.

### Phase 6 — MCP App host and MCP 2.0 (closes 2 rows, largest single item)

| Step | Change                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------- |
| 6.1  | Sandboxed `<iframe>` host with a `postMessage` protocol modelled on the desktop's host↔guest pair |
| 6.2  | No network, no top-level navigation, no clipboard, CSP from the app origin                        |
| 6.3  | Guest entrypoints: sidebar, panel, file editor, forms — each an explicit manifest field           |
| 6.4  | MCP 2.0 events only after an SDK version that supports them; do not hand-roll a transport         |

Exit gate: a fixture MCP App renders in the host and a form submit reaches the guest, with the
sandbox proven by a denied `fetch` and a denied navigation.

Cost: **L**. Risk: high — untrusted code execution inside the app origin.

| Capability          | Why it stays out                                                                                                                 |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Computer Use        | Needs OS permissions and a per-app allowlist. Desktop itself is BLOCKED here without a UI decision.                              |
| Mobile remote relay | Needs a hosted relay and a second identity. Product change, not parity.                                                          |

| Sub-agents          | Blocked upstream: the gateway flattens the `collaboration` namespace for translated models. Fix belongs in `open-sse`, not here. |

## 4. Ordering rationale, and what must not be skipped

Phase 0 before everything: a write verb without a policy store is a remote code execution surface
with extra steps. The desktop app earns that capability by being a native process with a sandbox;
codex-web earns it only by refusing the default-open path.

Phase 1 before Phase 2: git writes are filesystem writes with a nicer UI. Build one gate, use it
twice.

Phase 3 independent of 1–2: it is a wire-format change, so it can ship in parallel with Phase 1 if
two agents work at once — which is exactly what happened for the 2026-11-02 BYOK/memories/git batch.

## 5. Gate for every phase

Unchanged from the repo contract, and no phase is "done" without it:

```bash
bun run verify          # check + lint + unit + build
bunx playwright test    # 102 tests x 3 projects: iPhone SE, iPhone 13, Desktop Chrome
bun run test:dev        # dev-server hydration + navigation, desktop project only
```

Plus, per phase: one spec that proves the **denied** path, and one line added to
`docs/progress.md` naming what is still not implemented. A parity row that is claimed without a
runtime probe is the mistake `docs/view-audit-2026-11-01.md` was written about.

Three things a reader should not over-read:

1. **Phase 1 is a gate, not an agent.** The loop, the caps and the refusal path are real and
   tested; the execution deps are absent, so a tool call currently ends in a policy refusal. That
   is the honest state and the reason `/api/ai/chat` passes no `tools` object.
2. **Phase 4 backend has no client.** The Convex functions work and are tested; the UI still uses
   the local store. Wiring the client is a separate change with its own migration test.
3. **Phase 5 records, does not run.** Deliberate (see the phase table), and the e2e test asserts
   the copy says so.

# Accessibility audit and fixes (2026-11-02)

Scope: the SvelteKit workspace shell (`slices/workspace-shell/`) and the chat/output views
under `src/lib/views/`. Every defect below was reproduced in a real browser before it was
changed. Each has a Playwright test in `tests/a11y.e2e.ts` that fails if the defect returns.
No new dependency: `@playwright/test` only, no axe.

## Fixed

### 1. Escape from a dialog opened by a menu item dropped focus on `<body>`

`Settings…` and `Keyboard Shortcuts` live inside bits-ui menubar/dropdown items, and those
items unmount with their menu. bits-ui's close-auto-focus then restores focus to a node that
is no longer connected, so `document.activeElement` ended up as `<body>` — a keyboard user
lost their place entirely and had to Tab from the top of the document.

Reproduced: `getByRole('menuitem', { name: 'Edit' })` → `Settings…` → `Escape` →
`document.activeElement === document.body`.

Fix: remember the open menu trigger before the dialog opens
(`rememberMenuTrigger()`), and restore it on close when and only when the closing overlay
left focus on `<body>` (`restoreOverlayFocus()` / `restoreOverlayFocusNow()`). It never
steals focus from a surface that already claimed it.

Tests:

- `escape-from-the-settings-window-opened-by-a-menu-item-returns-focus-to-that-menu`
- `escape-from-the-shortcuts-dialog-returns-focus-to-the-help-menu`

### 2. `#sidebar-toggle` claimed `aria-expanded` with no `aria-controls`

The toggle changes the visibility of the session drawer, but nothing told assistive
technology which region it expands, so `aria-expanded` was a state with no object.

Fix: `aria-controls="chat-sessions"` on the toggle, `id="chat-sessions"` on the
`<aside aria-label="Chat sessions">`. The id holds in both modes (collapsed rail and
off-canvas drawer), which the test asserts by resizing.

Test: `the-sidebar-toggle-points-aria-controls-at-the-session-drawer-it-expands`

### 3. The launcher tabpanel was labelled by an id that did not exist

`#output-panel-workspace-home` carries
`aria-labelledby="output-tab-workspace-home"`, but no tab exists until the launcher is
opened as a tab — on a fresh load the reference resolved to nothing and the panel had no
name.

Fix: point `aria-labelledby` at the tab only while that tab is open, and give the panel its
own `aria-label` otherwise.

Test: `every-tabpanel-is-named-by-an-id-that-exists`

### 4. The server-controls trigger pointed `aria-controls` at an unmounted panel

`aria-controls={panelId}` was always present; the panel it names only renders while the
popover is open, so the reference dangled in the closed state.

Fix: emit `aria-controls` only while the panel is mounted (`src/lib/RuntimeControls.svelte`).
`aria-expanded` already carried the state.

Test: `the-server-controls-trigger-only-names-a-panel-while-that-panel-is-mounted`

### 5. "Skip to chat" was a no-op whenever the output panel filled the view

The skip link called `focusChatComposer()`, which focuses the chat region. With the output
panel expanded — or on a narrow viewport showing only the output — that region is
`display: none` + `inert`, so the focus call did nothing and activation left focus on the
link. This is exactly the case where a keyboard user most needs a way back to the composer.

Fix: when the chat region is not visible, run the same `go('chat')` path the rail button
uses, then focus the composer. The hash follows, so the state is consistent with what the
rail does.

Test: `skipping-to-chat-while-the-output-panel-fills-the-view-reveals-and-focuses-the-composer`

### 6. Menu surfaces and their keyboard highlight were the same colour

`.workspace-overflow-menu` used `background: var(--color-hover)` and so did
`[data-highlighted]` / `:hover` on its items: measured 1.00:1 between the highlighted item
and the menu behind it. Combined with `outline: none` on the items, a keyboard user
arrowing through the More / user / chat menus had no visible cursor at all.

Reproduced by inspecting the computed background of `document.activeElement` after
`ArrowDown`: both `rgb(44, 44, 44)`.

Fix: `:focus-visible` outline on `.workspace-overflow-item`, `.workspace-menu-item` and
`.workspace-menubar-item`, using `--color-ink` at 2px with a negative offset. The menu
background itself is unchanged so pointer users see the same surface as before; the
indicator is additive. Contrast of the ring against the menu surface is asserted at ≥ 3:1.

Test: `a-keyboard-highlighted-menu-item-is-distinguishable-from-the-menu-surface`

### 7. Real tables with no caption or label

Five `<table>` elements (Snake engine results, its warmup breakdown, the measured-steps
table, both SnakeHistory tables, the Playground comparison) had `<th>` cells but no
`<caption>` and no `aria-label`, so a screen reader announced an unnamed table. The
`Providers` table already did this correctly and was used as the pattern.

Fix: `.sr-only` `<caption>` on each, describing what the table compares.

Test: `every-table-on-the-engine-comparison-screen-has-an-accessible-name`

### 8. The composer used `aria-expanded` with no popup role

`#chat-message` carried `aria-expanded` + `aria-controls` + `aria-activedescendant` for the
slash/`@` picker, and `aria-autocomplete="list"`, but its exposed role was `plain textbox`.
`aria-expanded` on a plain textbox is not a valid combination — the accessibility tree
showed `expanded` only once the role was `combobox`.

Verified over CDP (`Accessibility.getPartialAXTree`): role `textbox`, properties
`autocomplete=list` but no `expanded`.

Left as a **note**, not fixed — see below. The test asserts the parts that do hold today
(`aria-autocomplete="list"`, `aria-controls` resolving to a `role="listbox"`,
`aria-activedescendant` resolving to an `aria-selected="true"` option).

## Noted, not fixed (product decisions)

- **The composer is not a `combobox`.** Giving it `role="combobox"` would make
  `aria-expanded` valid, and it is a one-line change, but it also changes how every screen
  reader announces the primary input of the app and how the picker is browsed (combobox
  pattern vs. free text). That is a product decision about the chat surface, not a defect
  in the shell, and it belongs with whoever owns `Chat.svelte`'s interaction model.
- **The timeline announces replies only after the run settles.** `role="log"` +
  `aria-live="polite"` are correct, and `aria-busy="true"` during a run is deliberate: it
  stops the streaming caret and per-token text from being read out. The effect is that the
  finished reply is announced once, not incrementally. Incremental announcement would be
  the alternative, and it is a UX choice, not a bug.
- **`--color-ink-3` is legible but only just on the composer.** `#aaaaaa` on `#353535` is
  5.28:1, above 4.5:1. It is asserted in the palette test so a future darkening fails.
  Tightening it further would flatten the placeholder against real text; left alone.
- **The menubar/dropdown highlight (`--color-hover` on `--color-panel-2`) is 1.08:1** for
  pointer users. Pointer users do not need a WCAG contrast minimum on a transient hover
  state, and raising it would change the whole palette's hover treatment. The keyboard
  indicator is fixed separately (item 6); the hover colour is left as designed.
- **The settings-window search filters categories but the dialog keeps its own heading
  level order** (`h2` inside a `Dialog.Title`). Reordering headings inside a portalled
  dialog changes what a screen reader user hears first on open, which is a design call.

## Deliberately not touched

No product behaviour changed: the only functional edits are focus return, `aria-controls`
emission, the skip link's fallback path, and `aria-labelledby`/`aria-label` selection. No
colour was changed; contrast is asserted, not adjusted.

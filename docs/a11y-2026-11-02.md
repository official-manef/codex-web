# Accessibility audit and fixes (2026-11-02)

Scope: the SvelteKit workspace shell (`slices/workspace-shell/`) and the chat/output views
under `src/lib/views/`. Every defect below was reproduced in a real browser before it was
changed. Each has a Playwright test in `tests/a11y.e2e.ts` that fails if the defect returns.
No new dependency: `@playwright/test` only, no axe.

## Fixed

### 1. Escape from a dialog opened by a menu item dropped focus on `<body>`

`Settings…` and `Keyboard Shortcuts` live inside bits-ui menubar/dropdown items, and those
items unmount with their menu. bits-ui's close-auto-focus then restores focus to a node that
is no longer connected, so `document.activeElement` ended up as `<body>` — a keyboard user
lost their place entirely and had to Tab from the top of the document.

Reproduced: `getByRole('menuitem', { name: 'Edit' })` → `Settings…` → `Escape` →
`document.activeElement === document.body`.

Fix: remember the open menu trigger before the dialog opens
(`rememberMenuTrigger()`), and restore it on close when and only when the closing overlay
left focus on `<body>` (`restoreOverlayFocus()` / `restoreOverlayFocusNow()`). It never
steals focus from a surface that already claimed it.

Tests:

- `escape-from-the-settings-window-opened-by-a-menu-item-returns-focus-to-that-menu`
- `escape-from-the-shortcuts-dialog-returns-focus-to-the-help-menu`

### 2. `#sidebar-toggle` claimed `aria-expanded` with no `aria-controls`

The toggle changes the visibility of the session drawer, but nothing told assistive
technology which region it expands, so `aria-expanded` was a state with no object.

Fix: `aria-controls="chat-sessions"` on the toggle, `id="chat-sessions"` on the
`<aside aria-label="Chat sessions">`. The id holds in both modes (collapsed rail and
off-canvas drawer), which the test asserts by resizing.

Test: `the-sidebar-toggle-points-aria-controls-at-the-session-drawer-it-expands`

### 3. The launcher tabpanel was labelled by an id that did not exist

`#output-panel-workspace-home` carries
`aria-labelledby="output-tab-workspace-home"`, but no tab exists until the launcher is
opened as a tab — on a fresh load the reference resolved to nothing and the panel had no
name.

Fix: point `aria-labelledby` at the tab only while that tab is open, and give the panel its
own `aria-label` otherwise.

Test: `every-tabpanel-is-named-by-an-id-that-exists`

### 4. The server-controls trigger pointed `aria-controls` at an unmounted panel

`aria-controls={panelId}` was always present; the panel it names only renders while the
popover is open, so the reference dangled in the closed state.

Fix: emit `aria-controls` only while the panel is mounted (`src/lib/RuntimeControls.svelte`).
`aria-expanded` already carried the state.

Test: `the-server-controls-trigger-only-names-a-panel-while-that-panel-is-mounted`

### 5. "Skip to chat" was a no-op whenever the output panel filled the view

The skip link called `focusChatComposer()`, which focuses the chat region. With the output
panel expanded — or on a narrow viewport showing only the output — that region is
`display: none` + `inert`, so the focus call did nothing and activation left focus on the
link. This is exactly the case where a keyboard user most needs a way back to the composer.

Fix: when the chat region is not visible, run the same `go('chat')` path the rail button
uses, then focus the composer. The hash follows, so the state is consistent with what the
rail does.

Test: `skipping-to-chat-while-the-output-panel-fills-the-view-reveals-and-focuses-the-composer`

### 6. Menu surfaces and their keyboard highlight were the same colour

`.workspace-overflow-menu` used `background: var(--color-hover)` and so did
`[data-highlighted]` / `:hover` on its items: measured 1.00:1 between the highlighted item
and the menu behind it. Combined with `outline: none` on the items, a keyboard user
arrowing through the More / user / chat menus had no visible cursor at all.

Reproduced by inspecting the computed background of `document.activeElement` after
`ArrowDown`: both `rgb(44, 44, 44)`.

Fix: `:focus-visible` outline on `.workspace-overflow-item`, `.workspace-menu-item` and
`.workspace-menubar-item`, using `--color-ink` at 2px with a negative offset. The menu
background itself is unchanged so pointer users see the same surface as before; the
indicator is additive. Contrast of the ring against the menu surface is asserted at ≥ 3:1.

Test: `a-keyboard-highlighted-menu-item-is-distinguishable-from-the-menu-surface`

### 7. Real tables with no caption or label

Five `<table>` elements (Snake engine results, its warmup breakdown, the measured-steps
table, both SnakeHistory tables, the Playground comparison) had `<th>` cells but no
`<caption>` and no `aria-label`, so a screen reader announced an unnamed table. The
`Providers` table already did this correctly and was used as the pattern.

Fix: `.sr-only` `<caption>` on each, describing what the table compares.

Test: `every-table-on-the-engine-comparison-screen-has-an-accessible-name`

### 8. The composer used `aria-expanded` with no popup role

`#chat-message` carried `aria-expanded` + `aria-controls` + `aria-activedescendant` for the
slash/`@` picker, and `aria-autocomplete="list"`, but its exposed role was `plain textbox`.
`aria-expanded` on a plain textbox is not a valid combination — the accessibility tree
showed `expanded` only once the role was `combobox`.

Verified over CDP (`Accessibility.getPartialAXTree`): role `textbox`, properties
`autocomplete=list` but no `expanded`.

Left as a **note**, not fixed — see below. The test asserts the parts that do hold today
(`aria-autocomplete="list"`, `aria-controls` resolving to a `role="listbox"`,
`aria-activedescendant` resolving to an `aria-selected="true"` option).

## Noted, not fixed (product decisions)

- **The composer is not a `combobox`.** Giving it `role="combobox"` would make
  `aria-expanded` valid, and it is a one-line change, but it also changes how every screen
  reader announces the primary input of the app and how the picker is browsed (combobox
  pattern vs. free text). That is a product decision about the chat surface, not a defect
  in the shell, and it belongs with whoever owns `Chat.svelte`'s interaction model.

  > **Resolved in the second pass** — see §2 below. It is now `role="combobox"`.

- **The timeline announces replies only after the run settles.** `role="log"` +
  `aria-live="polite"` are correct, and `aria-busy="true"` during a run is deliberate: it
  stops the streaming caret and per-token text from being read out. The effect is that the
  finished reply is announced once, not incrementally. Incremental announcement would be
  the alternative, and it is a UX choice, not a bug.

  > **Upheld in the second pass** — measured, and it works as described. Two adjacent
  > defects in the same area were fixed instead; see §1 below.

- **`--color-ink-3` is legible but only just on the composer.** `#aaaaaa` on `#353535` is
  5.28:1, above 4.5:1. It is asserted in the palette test so a future darkening fails.
  Tightening it further would flatten the placeholder against real text; left alone.
- **The menubar/dropdown highlight (`--color-hover` on `--color-panel-2`) is 1.08:1** for
  pointer users. Pointer users do not need a WCAG contrast minimum on a transient hover
  state, and raising it would change the whole palette's hover treatment. The keyboard
  indicator is fixed separately (item 6); the hover colour is left as designed.
- **The settings-window search filters categories but the dialog keeps its own heading
  level order** (`h2` inside a `Dialog.Title`). Reordering headings inside a portalled
  dialog changes what a screen reader user hears first on open, which is a design call.

## Deliberately not touched

No product behaviour changed: the only functional edits are focus return, `aria-controls`
emission, the skip link's fallback path, and `aria-labelledby`/`aria-label` selection. No
colour was changed; contrast is asserted, not adjusted.

# Second pass (2026-11-02, later the same day)

Scope: the five items the first pass deferred. Everything below was reproduced in a real
browser against the built app before it was changed. `tests/a11y.e2e.ts` grew from 36 to
102 tests (34 cases × 3 viewports) and none of the first pass's tests were rewritten.

Two notes on method, because they changed how the tests are written:

- `test.use({ reducedMotion })` and `test.use({ forcedColors })` **do not reach the page in
  this setup** — measured with `matchMedia` inside the document, both read `false`. The
  tests therefore call `page.emulateMedia()` and assert the preference is live before
  measuring. A media-query test that never applied the query is a false pass.
- Reduced-motion tests only pass against a **production build**. In `vite dev` the Svelte
  scoped styles arrive through separate stylesheet modules whose cascade order does not match
  the built sheet, so transitions survive the override. `playwright.config.ts` builds and
  previews, so the gate is honest; a `--dev` run is not.

## 1. Screen-reader announcement policy — the per-run choice was right, the switching case was not

The first pass called per-run (not per-token) announcement a UX choice. That is only
defensible if the finished reply is genuinely announced **once** and nothing else is dropped
in. Measuring mutation state at each commit (`MutationObserver` recording `aria-busy` at the
moment of the record) showed:

- **Per-run announcement works as claimed.** A real run produces several DOM commits while
  `aria-busy="true"` and then commits the settled reply while it is `false`. Asserted: every
  non-busy mutation already contains the _complete_ settled text, so a screen reader never
  reads a half-written prefix and never reads the same reply twice.
- **Defect: every turn was an unnamed `article`.** Inside a `role="log"`, screen readers
  navigate by article. All of them announced as just "article". Fixed by naming them from the
  data that already exists: `aria-label="Your message, <time>"` on the user article and
  `aria-label="Reply from <device>"` on the assistant article — plus names on the
  in-flight articles so a turn is identifiable while it is still streaming.
- **Defect: switching conversations replayed the whole history.** `readSession()` cleared
  `sessionLoading` _before_ `await tick()`, i.e. before the transcript had committed. The
  entire new history therefore landed while `aria-busy` was already `false`, and a screen
  reader announced the full conversation as one insertion. Fixed by clearing `sessionLoading`
  after the transcript commits; the log now reports `busy` for the duration of the swap.

Tests: `a streaming run keeps the log busy and announces the reply exactly once when it
clears`, `every turn and reply carries an accessible name`, `switching conversations does not
replay the whole history into the live region`.

## 2. Form semantics — the composer became a real `combobox`

**Decision: adopt `role="combobox"`, not drop the attributes.** Reasoning:

1. The composer already _is_ a combobox. It has `aria-autocomplete="list"`, an
   `aria-activedescendant` that tracks a `role="listbox"` of `role="option"` children, and an
   expand/collapse state. That is the combobox pattern with the role missing.
2. Dropping the attributes would mean deleting `aria-expanded`/`aria-controls`/
   `aria-activedescendant` and going back to a plain textarea. The picker would then have **no
   programmatic relationship to its popup at all** — strictly worse for a screen-reader user
   than the status quo, which at least exposed `aria-autocomplete`.
3. The cost of the combobox role is announcement phrasing: a screen reader says "combo box"
   rather than "edit text, multi line". That is correct here, because the control does control
   a listbox. It would be the wrong call for a plain message box with no picker.
4. It is legal for this element. Per ARIA in HTML, `<textarea>` allows _only_ `role=textbox`
   — but this is not a bare `<textarea>`: it is a component whose contract is "input that
   controls another element that can pop up to set its value", which is the `combobox`
   definition. The picker is the popup. Verified over CDP that Chromium now exposes role
   `combobox` with `expanded`, `hasPopup=listbox` and `autocomplete=list` — none of which
   appeared on the plain textbox.

The state was previously **dropped from the accessibility tree entirely**: a plain textbox
with `aria-expanded` exposed no `expanded` property, so the picker's open/closed state was
invisible to assistive technology even though the markup claimed it.

### Second composer fix: the picker's own controls were unreachable

`onKey` cancelled `Tab` whenever the picker was open, to dismiss it. That meant the picker's
`Close picker` button and its category toggles — both rendered after the textarea in DOM
order — could never receive focus. A keyboard user could arrow through options and press
Escape, but could not switch category at all: that was pointer-only. Fixed by letting `Tab`
through; the picker stays open while focus walks into it.

The category row was also `role="tablist"` with `role="tab"` children each carrying
`aria-controls="composer-resources"` — three tabs all controlling one listbox, with no
tabpanel. That is invalid and it announced as a tab set that did not behave like one. It is
now a labelled `role="group"` of toggle buttons using `aria-pressed`, which is what it is.

Tests: `the composer is a real combobox and the state survives into the accessibility tree`,
`the picker is fully operable by keyboard alone`, `every visible form control has a
programmatic label`, `the composer keeps a single accessible name and does not rely on its
placeholder`.

## 3. Keyboard map — one control was unreachable, and it is fixed

Every interactive control was enumerated and Tab-walked at 1400×900, 1280×800 and 375×667:

| ------------------------ | -------------------------------- | ------------------------------------------------ |
| Composer                 | yes                              | yes (Enter sends)                                |
| Send                     | yes                              | yes                                              |
| Stop                     | yes                              | yes (real `<button>`, `tabIndex` 0)              |
| Attach / add tools       | yes                              | yes (Enter opens picker)                         |
| Model picker             | yes                              | yes (Enter opens, arrows move the active option) |
| Session list             | yes (drawer toggle below 1100px) | yes                                              |
| Tab strip                | yes, roving tabindex             | yes (arrows, Home/End, Delete closes)            |
| Tab picker               | yes                              | yes (opens with focus on its search field)       |
| Output panel toggle      | yes                              | yes (label follows state)                        |

**Defect found and fixed:** the picker's category toggles (see §2). Everything else was

**Also fixed:** the rail marked the current app with `.rail-active` only, i.e. a background

Tests: `the shell controls are all reachable in one Tab pass`, `send, stop, attach and the

expose their controls to the keyboard`, `no visible enabled control is parked outside the Tab
order`.

## 4. Reduced motion — the guard was real but incomplete

The blanket rule (`animation-duration: 0.01ms`, `transition-duration: 0.01ms`,
`animation-iteration-count: 1`) does work: on a production build **zero** elements keep a
running transition or animation. Two things were not covered:

- **`scroll-behavior: smooth`** was nowhere in the app, but nothing enforced it either, and
  the blanket duration override does not touch it. Added `scroll-behavior: auto !important`
  under the same query so a future smooth scroll cannot slip past.
- **Infinite animations were only reduced, not removed.** `0.01ms` × `1` iteration already
  effectively stops the typing dots and the streaming caret, but `animation: none` states the
  intent and survives a future change to either the duration or the iteration count.

Both are `@media (prefers-reduced-motion: reduce)` — motion is untouched for everyone else,
and there is a test that asserts that (`motion is preserved for everyone else`), so the guard
cannot be satisfied by deleting motion outright.

The shell already had two per-component `prefers-reduced-motion` blocks
(`MessageFrame`, `ChatListRow`) plus one in `app-laya.css`; those stay, and the global rule
now covers what they miss.

Tests: `no element keeps a running transition or animation`, `smooth scrolling is off for a
reduced-motion user`, `the typing indicator and streaming caret do not animate`, `motion is
preserved for everyone else`.

## 5. Forced colours — usable, but three states became invisible

The UI **stays usable**: text takes the system pair, focus rings are visible, the disabled
Send button keeps its system colour, and the assistant bubble's `1px` border survives. Three
meaningful states did not, because each was carried only by an author background:

- **Current rail item.** `rail-active` was `background: var(--color-nav-active)`; forced
  colours replaces it with the page background, so every app looked equally current. Fixed
  with a `Highlight` outline, which is the system colour reserved for exactly this.
- **Selected output tab.** `.output-tab.selected` was a background plus border tint; both
  collapsed to the idle values and the strip showed no position. Fixed with
  `border-color: Highlight` and a bolder label.
- **Selected conversation.** `.session-selected` was a background tint only. Fixed with a
  `Highlight` outline.
- **Composer focus ring.** The composer draws a `1px` outline on its wrapper rather than on
  the textarea, and the wrapper's colour came from a custom property that the palette swap
  flattens. The base `:focus-visible` rule targets the textarea, which has `outline: none`, so
  nothing was left. Fixed with a `2px Solid Highlight` ring under the query.
- **Message bubble tones.** User and assistant bubbles were separated by background alone.
  Both now carry a `1px CanvasText` border, so the two tones stay distinguishable without
  colour.

Reported but **not** fixed: pointer hover and roving-menu highlight share `--color-hover` and
therefore collapse into one another in forced colours (1.0:1). Forced colours deliberately
removes hover styling, the keyboard indicator is separate and does work, and there is no
non-colour signal that would not also change the pointer experience. Left as designed.

Tests: `the current rail item and the selected tab keep a visible state`, `text and controls
keep readable system colours and a visible focus ring`, `the composer keeps a border in
forced colours so both tones stay distinguishable`.

## Still deferred

- **The settings dialog heading order** (`h2` inside `Dialog.Title`) from the first pass is
  unchanged: reordering headings inside a portalled dialog changes what a screen reader hears
  first on open, and that is a design call, not a defect.
- **The timeline has no announcement for a _failed_ turn** beyond the error text landing in
  the log. A dedicated `role="alert"` would be louder but would also fire for recoverable
  provider errors; judged a product decision.
- **`aria-atomic`** is not set on the log. Setting it to `true` would make each announcement
  re-read the entire conversation; the per-article names make `false` (the default) correct.
